# Android Storage Architecture  
Android devices use a Linux-style filesystem layout.  The *internal storage* (often a single ext4 or F2FS partition) contains `/data` (app-private data and system files) and `/system` (read-only OS). Each app’s private data lives under `/data/data/<package>` (or equivalently `/data/user/0/<package>` for user 0).  In contrast, “external” or **shared** storage is a logical area where media and documents are stored. On modern Android this is usually implemented by **emulated storage**: the actual files reside under `/data/media/0/`, but are exposed to apps and users via paths like `/sdcard` or `/storage/emulated/0`.  (In other words, `/sdcard` and `/storage/emulated/0` are FUSE/sdcardfs mounts that map onto `/data/media/0`.)  Removable SD cards appear under `/storage/<UUID>` but may also be aliased to `/sdcard` in some cases. In short, internal NAND storage and microSD cards use Linux filesystems (ext4/F2FS vs FAT32/exFAT), but *mount points* differ: internal shared storage is a virtual view of `/data/media`, while an SD card is a separate block device mounted in external storage.  

Official Android docs summarize this by distinguishing *app-specific* (internal) vs *shared* (external) storage.  App-specific internal files (`getFilesDir()`, etc.) are private and removed on uninstall.  Shared media (images, videos, etc.) reside in external storage (e.g. `/storage/emulated/0/DCIM`) and are indexed by **MediaStore**.  On Android 11+, accessing other apps’ shared media requires the `READ_EXTERNAL_STORAGE` permission (or scoped-storage APIs).  Removable SD cards are treated as part of external storage (e.g. `/storage/<label>` or `/sdcard` symlink).  

**Emulated Storage (sdcardfs):**  Modern Android (Android 7+) uses a kernel “sdcardfs” driver (replacing older FUSE) to enforce permissions on `/sdcard`.  The result is that the shared storage is *not* a true Unix filesystem: all files under `/sdcard` appear with fixed owner UID/GID and permission mask that apps cannot change.  The real data is in `/data/media` (a normal ext4/F2FS filesystem), but only special system services (MediaProvider, the “sdcard” daemon) expose it via `/sdcard`.  This means apps cannot change permissions on `/sdcard` files (chmod/chown have no effect).  It also means that without root, an app sees only the FUSE view (via MediaStore or SAF), not the raw underlying partition.  

**Filesystem Types:**  Most phones use ext4 or F2FS on internal memory, both journaling filesystems.  Removable SD cards are usually formatted as FAT32 or exFAT (unless adopted as encrypted storage on Android 9+).  FAT/exFAT have no journaling: deleting a file simply removes its directory entry and zeroes its FAT/exFAT allocation table entries.  (As one recovery expert notes, “after deletion or formatting [of FAT], non-contiguous or fragmented files cannot be recovered in one piece, because the file system metadata pointing to individual clusters is zeroed”.)  By contrast, ext4/F2FS deletion unlinks the inode and marks blocks free, but metadata like the journal may briefly contain remnants.  

**MediaStore:**  Android provides a MediaStore content provider that maintains a SQLite database of media (images, video, audio).  The system’s media scanner updates MediaStore when new files appear or are deleted. MediaStore does *not* store the raw media; it merely indexes file metadata (paths, timestamps, thumbnails, etc.) for quick access.  For example, Android docs state that the framework “provides an optimized index into media collections, called the Media Store, that lets users retrieve and update these media files”. When a photo is taken or a file added to DCIM/Pictures, MediaStore inserts a record. When a file is deleted (e.g. via Gallery or camera app), the system deletes the file on disk and MediaStore removes its record during the next media scan. 

**Filesystem Behavior on Deletion:**  On Linux filesystems (ext4/F2FS), deleting a file essentially does: remove its directory entry, decrement inode link count, and mark its blocks as free in the block allocation bitmap. The data blocks typically remain intact until overwritten, unless filesystem mount options or storage drivers send a discard/TRIM to the storage.  On UFS-based flash (typical internal storage), Android does *not* continuously send TRIM on each delete; instead, it relies on periodic `fstrim` (often run during idle or charging). When TRIM/discard *does* occur, the flash controller erases those blocks in the background. Forensic analyses of SSDs/flash note that TRIM causes rapid data erasure: “the evidence self-destruction process is triggered with the TRIM command issued by the OS at the time the user deletes a file… formatting the disk, or deleting a partition”. In practice, this means shortly after deletion (and a future TRIM), the deleted file’s data may be unrecoverable. Removable SD cards (FAT/exFAT) generally do *not* implement TRIM, so deleted data can linger much longer (until overwritten by new data).

**Summary:**  Android devices present a layered storage architecture: an encrypted, flash-backed internal filesystem (/data) hosting an *emulated* shared storage (`/sdcard` via sdcardfs), plus optional FAT/exFAT external SD cards.  The MediaStore index lives on the internal data partition.  When a photo/video is deleted, it is first removed from MediaStore and then from the filesystem; only after that can any low-level recovery attempt access its raw remnants.  

# File Deletion Lifecycle on Android  
When the user deletes a photo or video (e.g. using the Gallery or camera app), the following steps occur:

1. **Application action:** The Gallery/Camera app typically calls `ContentResolver.delete()` on the MediaStore URI or deletes the file via the filesystem API.  
2. **MediaStore update:** The system’s MediaProvider receives a content-delete request (or later a scan notices the missing file) and removes the corresponding row from the MediaStore database. From that point, user-facing apps won’t list it.  
3. **File removal:** The file’s directory entry is unlinked. On ext4/F2FS, the inode’s link count drops to 0 and blocks are marked free in the filesystem metadata. On FAT/exFAT, the directory entry is removed and the FAT chain is cleared.  
4. **Metadata handling:** The inode (or equivalent) is freed; its timestamp/metadata may or may not be preserved briefly in the journal. In ext4, the journal might still contain older data segments, but those are typically overwritten by later writes. No immediate secure-erase happens at the filesystem level.  
5. **TRIM/Discard:** If the filesystem is mounted with discard or a scheduled `fstrim` runs, the OS issues a TRIM command for the freed blocks. On UFS flash, this tells the flash controller the blocks can be erased in the background. Once erased, the original data bits are gone. Otherwise, without discard (or on SD cards), data remains in flash memory until overwritten.  
6. **Garbage Collection:** The flash storage’s own wear-leveling and garbage collection may asynchronously relocate and erase blocks that held deleted data, further eliminating recovery chances.  

**Recoverability:** Immediately after deletion but before any TRIM or overwrite, the raw file data still resides in flash. A recovery tool (with sufficient access) could scan the freed space to reconstruct it. But once TRIM occurs or new data overwrites those blocks, recovery becomes impossible. In practice, small OS writes (logs, app cache writes, etc.) can quickly overwrite deleted file blocks. This explains why recovery tools often succeed only if run **very soon** after deletion: “some remnants of deleted data can still be recovered from an SSD [or UFS] drive… if the TRIM command is NOT issued”. In short, deleted files are recoverable only in a brief window (possibly seconds to minutes) unless the device is locked down or powered off quickly.  

# Recovery Tools and File-Carving Techniques  
Tools like DiskDigger, PhotoRec, Recuva, etc., work by scanning storage for traces of known file types. They commonly use **file carving**: searching raw blocks for file signatures (magic numbers) and extracting contiguous data matching a format. For example, JPEG files start with bytes `0xFFD8 FFE0` (or similar) and end with `0xFFD9`; PNG files have a fixed header (`89 50 4E 47 0D 0A 1A 0A`) and an IEND trailer. MP4/MOV/HEIC (ISO-base) files have box structures (`ftyp` at the start and `mdat`/`moov` atoms) that carving tools can recognize. Tools may also use embedded metadata (EXIF, file lengths) to bound recovery. If a file’s original name or path is lost, carving simply recovers the content as a new file (often named by signature and offset). Fragmented files (non-contiguous on disk) pose a challenge: FAT-based recovery tools note that “non-contiguous [FAT] files cannot be recovered in one piece” because the cluster-chain pointers are gone. Thus if a JPEG is split into fragments, a simple header-footer scan might recover only the first contiguous portion, leading to incomplete images. Some advanced tools try “gap carving” or manual cluster-chaining, but results are hit-or-miss. It’s also common that thumbnails or small cached copies survive even when the main file is gone: e.g. Android’s MediaStore maintains thumbnail caches, and apps like WhatsApp or Facebook often keep their own resized copies of images, which carving tools can sometimes find.  

**Scanning Methods:**  
- *Metadata scanning:* Some forensic tools read filesystem metadata (FAT directory entries, ext4 inodes) looking for “deleted” flags. FAT marks deleted entries with a special 0xE5 character; ext4 sets a flag in the inode. Tools running on an imaged block-level copy (or with raw block access) can enumerate such entries. However, on modern Android non-root, apps cannot read this raw metadata.  
- *Free-space scanning (carving):* The most common approach is to scan unallocated space for file signatures. As one forensic study notes, tools like Foremost (and by extension DiskDigger) recovered “deleted files, deleted file fragments and hidden data files… from slack/free spaces of the images”, implying a raw-carve. This is how DiskDigger operates under the hood: looking byte-by-byte for photo/video file headers.  
- *MediaStore or thumbnail tables:* Some tools query MediaStore’s Thumbnails table or scan app cache directories for thumbnail images. A deleted photo’s thumbnail (usually a smaller JPEG) might persist in `/DCIM/.thumbnails` or MediaStore’s thumb DB. Recovering a thumbnail is technically easier (it’s smaller and contiguous) but yields only a tiny version of the image. DiskDigger on PC (or Android) often reports “thumb” as a type of recovery.  

**DiskDigger specifics:** According to its documentation, DiskDigger presents two modes: “Basic scan” vs “Full scan”. The *basic* mode runs without root and is limited to file types accessible via normal APIs (typically JPEG/PNG on external storage). The *full* mode (requiring root) can open the raw `/data` partition and scan it, recovering many more file types. The site explicitly states: *“DiskDigger does not require your device to be rooted, [but] it is more likely to recover more photos and files if your device is rooted”*. On a rooted device, you can even choose the partition (e.g. “/data”) to scan. Without root, DiskDigger can only scan the publicly mounted storage (e.g. `/storage/emulated/0`) via Android’s media APIs.  

In practice, then:  
- **Non-root (app) recovery:** Tools can use MediaStore APIs or SAF to list and delete existing media, and may attempt to read caches/thumbnails. They **cannot** perform raw block scanning or carve files from internal storage. Non-root apps usually cannot recover truly deleted files from `/data`. They might find media in the OS’s “Trash/Recycle Bin” (see below) or in caches.  
- **Root recovery:** With root, an app (or ADB shell) can `dd` the block device (`/dev/block/...`) or call low-level utilities to image partitions, then run carving. Rooted tools can also inspect `/data/user/0/<app>/cache` or `/data/media/0/Android/data` for hidden copies. In essence, root removes the permission barrier, letting the app act like a forensic analyst scanning free space.  

# Scoped Storage and Android Versions  
Android’s storage model has changed substantially. From Android 6–9, apps could freely request `READ/WRITE_EXTERNAL_STORAGE` and access any path under `/storage`. Starting Android 10, **Scoped Storage** began restricting apps’ access to external files: apps can only see their own files and media types unless they use the Storage Access Framework or special permissions. On Android 11+, scoped storage is enforced for new apps (targeting API30+), and the old `WRITE_EXTERNAL_STORAGE` is essentially obsolete; instead a new `MANAGE_EXTERNAL_STORAGE` (“All files access”) permission exists but is seldom granted to Play Store apps. The **storage updates** in Android 11 documentation emphasize that apps cannot access arbitrary files on external storage without user action. For example, after Android 11 an app “cannot access the files in any other app’s data directory, even if the other app … made them world-readable”. Similarly, apps cannot scan the `/Android/data/` folder belonging to other apps.  

**Practical impact on recovery:** On Android 8–10, a recovery app with `WRITE_EXTERNAL_STORAGE` could enumerate most shared-media directories. On Android 11+, even with storage permission, it cannot directly list other apps’ directories and sees external storage mainly through MediaStore or SAF. Thus, techniques that worked on older Android (like reading any path under `/storage/emulated/0/DCIM`) are constrained. Without special privileges or root, a custom app on Android 11+ is largely confined to MediaStore queries and SAF user picks. Root (or `MANAGE_EXTERNAL_STORAGE` with user consent) relaxes this, but even MANAGE only covers external, not `/data/data`.  

Additionally, Android 12–14 introduced more restrictions on background access and ephemeral permissions. However, the core block-level deletion behavior did not fundamentally change: modern Android devices still use ext4/F2FS with periodic trim, and still respect file unlink semantics. Notably, Android 11’s scoped storage update did *not* eliminate the need to manage deleted files carefully; it just changed how apps request and access storage.  

# Internal vs Removable (microSD) Storage  
**File system:** Internal storage (ext4/F2FS) journals metadata and supports *file-based encryption* (FBE). In most modern devices (Android 11+), internal `/data` is encrypted with per-file keys tied to user credentials. Deleted file blocks, even if read, are encrypted fragments that cannot be understood without keys. Removable SD cards, however, use FAT32/exFAT and by default are not encrypted (unless formatted as “adoptable” by user choice on Android 9+). This means carved data from an SD card is plain; internal data is typically unintelligible without decryption keys.  

**Metadata:** FAT/exFAT maintains a simple table of cluster chains. When a file is deleted, its directory entry is marked deleted and the FAT entries are set to 0. This makes it relatively easy for carving tools (like PhotoRec) to read free clusters in sequence. In contrast, ext4/F2FS mark blocks free in a bitmap; without root, an app cannot read these free blocks. Also, FAT’s lack of journaling means there’s no hidden copy of file data after deletion, whereas ext4’s journal might temporarily hold a fragment (though hardly useful after commit).  

**Accessibility:** A microSD card can be physically removed and attached to a PC, allowing use of desktop recovery tools (Photorec, Recuva) on the raw card image. It can also be write-protected or imaged via card readers. Internal storage cannot be removed (except by chip-off hardware methods) and typically must be accessed via the device (ADB, root, or official backup APIs).  

**Recoverability:** Because of the above, deleting photos on a microSD is often *easier* to recover (especially soon after) than on internal NAND. The absence of encryption and TRIM, plus the simplicity of FAT, means standard carving usually works well on SD cards. By contrast, internal storage’s UFS controller and FBE can silently erase or encrypt deleted data, making full recovery from unrooted devices mostly impossible once the OS moves on.  

# Android Encryption and Deleted Data  
From Android 7 onward, devices typically use **File-Based Encryption (FBE)**. This means each user’s data area is split into *Credential Encrypted (CE)* and *Device Encrypted (DE)* zones, each with its own keys. Every file (or directory) is encrypted with a per-file key stored in the Android Keystore; the master keys are protected by the user’s PIN/pattern. For deleted-file recovery, FBE has two major effects: 

- **Encryption of stored data:** When a file is saved, it is encrypted on-disk. Thus, even if raw blocks remain after deletion, they contain ciphertext that cannot be deciphered without keys. Unless an attacker also obtains the user’s lockscreen credentials (or the device is in a “direct boot” unlocked state), the recovered data is gibberish. Even with credentials, the carver tool would have to decrypt file fragments, which is not typically done by consumer recovery apps. 

- **No plaintext snapshots:** Unlike a traditional disk, there is no unencrypted copy of file contents in slack space or unallocated areas, because ext4 with FBE encrypts data at write-time. Once a file is unlinked, its encrypted blocks become free; without keys, they are useless. 

Some older devices used full-disk encryption (FDE) on ext4, which similarly encrypted the entire data partition as one LUKS-like volume. Modern Samsung devices (like Galaxy A05s) often have hardware-backed AES on the NAND as well. In either case, the principle is the same: deleted data is protected by cryptographic keys that apps cannot access. 

**Practical recoverability:** In theory, one could image the flash and later brute-force keys or use manufacturer backdoors, but for an on-device recovery app this is *practically impossible*. The combination of FBE and TRIM means that almost any deleted blocks are both erased and encrypted. Thus, on an encrypted Android 14 phone, recovering raw deleted photos from `/data` is essentially *impossible* unless one has root and the decryption keys (e.g. via a forensic bootloader exploit). In contrast, an unencrypted SD card allows standard carving.  

# Samsung Galaxy (One UI) Considerations  
Samsung’s phones (like the Galaxy A05s on Android 14) have some vendor-specific features:  
- **Trash/Recycle Bin:** Samsung Gallery apps include a “Trash” (recently deleted) album. When a user deletes a photo in the Gallery, the file is moved to a hidden folder (e.g. `/DCIM/Trash` or a database record) for 30 days. During this period, the photo still exists in storage and could be easily recovered by reading the Trash album through the Gallery or possibly via MediaStore (though access is typically via the Samsung UI only). After expiration, the Trash entry is purged. This mechanism is not part of Android’s public API, so a third-party app cannot directly query the Samsung Trash – the best it can do is check if deleted files appear in *any* media database (unlikely) or scan the DCIM directory for a `Trash` folder. 

- **My Files and Cloud:** Samsung’s My Files app may also have a Recycle Bin (for any file). Deleted files there may linger in a `.recycle` directory. Samsung’s devices also often integrate with OneDrive (uploading Gallery photos), but recovery from the cloud would require user credentials and APIs beyond the device. There’s also Samsung Cloud (for older devices) but on newer devices it often just redirects to OneDrive. 

- **Thumbnail/Cache:** Samsung Gallery may cache thumbnails in a hidden DB or folder. Similarly, Google Photos (pre-installed) could have thumbnails/copies in its local cache. These are unlikely accessible to a third-party without root, but if found, they are usually very low resolution. 

- **File paths:** Samsung generally follows standard AOSP paths (`/DCIM/Camera`, etc.), so there is nothing special about where photos are stored beyond UI differences. Its adoption of FBE and UFS is typical for modern Android: internal storage is fast UFS with hardware encryption.  

- **Android 14 Security:** On this device, scoped storage and privacy restrictions of Android 12/13/14 fully apply. The user would need to grant the app the new `READ_MEDIA_IMAGES` permission (Android 13+) or `MANAGE_EXTERNAL_STORAGE` to scan media. Unrooted, the app cannot penetrate `/data/data` or `/Android/data` beyond SAF.  

In summary, there is no hidden trick in One UI that bypasses Android’s rules; the Galaxy A05s is “standard” from a storage perspective, apart from Samsung’s own Gallery/Trash apps. We treat Samsung Trash as a *special case of a restore point*, but any reliance on it is more an inference than an official recovery mechanism (and is basically outside a custom app’s reach). 

# Existing Recovery Tools Overview  
- **DiskDigger (Android app):** (as above) does basic scanning without root and full scanning with root. It specializes in images/videos; the free version only recovers JPEG/PNG (photos) unless rooted. The developer’s claims (from the site) are marketing but reflect reality: without root it can “undelete” photos by carving the *public* storage area. Rooted, it effectively does low-level carving on `/data`. 

- **PhotoRec/TestDisk:** Open-source tools (desktop/CLI) that carve many file types (JPEG, PNG, HEIC, MP4, etc.) on any image or drive. They require a PC or terminal; to recover from an Android phone you would typically use `adb` to pull a raw image of an SD card or an internal partition (if rooted). PhotoRec’s signature library (found in `sig/fot`) identifies headers for most common media formats. These tools show that raw carving is universal: they do not use filesystem metadata at all. 

- **Recuva/EaseUS/Dr.Fone/etc.:** These are commercial PC tools. For Android, they usually require connecting the device to a computer (often in USB debugging mode). They often *insist on root* for internal recovery, or they only work on SD cards. They may also offer cloud backup recovery. Their marketing claims should be taken skeptically: for example, many tout “no root needed” but in practice they either can’t reach internal flash (so they only scan external storage or cached files). Without independent documentation, we assume they do similar carving or use Android’s backup API. In general, any plausible recovery of truly deleted internal data on unrooted phones is extremely limited. 

- **Forensic tools (e.g. MSAB, Cellebrite):** These enterprise tools may use exploits to bypass Android security and image flash, but that’s beyond a normal app’s capabilities. They are not relevant for a consumer app on an unrooted modern phone. 

# What a Custom Android App Can Do  
- **Without Root:** Limited to the Android APIs. Primarily:  
  - Use **MediaStore queries** (with `READ_MEDIA_IMAGES/VIDEO` on Android 13+, or the old storage perms on earlier OS) to list *existing* media. Once a file is deleted, its MediaStore row is gone, so this yields only *existing* (not deleted) files. It can delete via MediaStore but not restore.  
  - Use **Storage Access Framework (SAF)** or Intent pickers to let the user select folders/files. SAF lets the app see only the URIs the user chooses. Deletion recovery via SAF is impossible unless the system shows deleted items (it doesn’t).  
  - Access **app-specific directories** and any external path it created itself. For example, if the app previously saved an image to `/sdcard/MyApp/`, it can revisit it. But it can’t read arbitrary other-app directories (Scoped Storage forbids it).  
  - Read **thumbnails** via MediaStore Thumbnails APIs (MediaStore.Images.Thumbnails). Note: retrieving thumbnails of deleted items is generally not possible because the MediaStore entry is gone, but a curious approach is scanning for hidden thumbnail files in DCIM (older Android used `/DCIM/.thumbnails` folders) – on Android 11+ this is inaccessible.  
  - Check **cache directories** it has permission to (own cache, maybe `/storage/emulated/0/Android/data/<package>/cache` if legacy storage). Other apps’ caches are off-limits without root.  
  - Exploit any **cloud sync** it can access: e.g. if the user has Google Photos backup enabled, the app could (theoretically) call Google Photos APIs if authorized by user, but this is effectively a separate backup rather than true file recovery.  
  - Use **MediaProvider columns**: Some have speculated that MediaStore might keep soft references to recently deleted files, but official docs indicate once a media is deleted the `_DATA` field (deprecated) is no longer valid and shouldn’t be used. So there’s no undelete flag.  

  In summary, a non-root app’s “recovery” is really: list existing media (including those in Trash if exposed), find any cached/copy of photos (e.g. in WhatsApp/media), and retrieve thumbnails or metadata. It can also scan removable SD if permitted by SAF. But it cannot carve unallocated space or read `/data/media` freely.  

- **With Root:** The app can execute commands as superuser. This unlocks:  
  - Direct block access: reading from `/dev/block/platform/.../by-name/userdata` or using `su` + `dd` to dump partitions. With this, a recovery function could invoke native carving libraries or tools on the raw image.  
  - Filesystem metadata: it could directly inspect `/data/data` and `/data/media` contents, including “lost+found” or journal. It could also try to remount filesystems with different flags (e.g. disable journaling, but Android usually mounts read-only for forensic).  
  - Partition imaging: Root can allow the app to save a full image to SD for PC analysis.  
  - Generally, root lets the app do almost anything a desktop tool can, limited only by code. Recovery of deleted files is still not guaranteed (because of encryption/TRIM), but theoretically possible if done immediately.  

- **Special permissions:** On Android 11+, an app can request the All-Files permission (`MANAGE_EXTERNAL_STORAGE`). If granted by the user (a very sensitive permission), the app can read/write most of external storage outside MediaStore. However, this STILL does *not* bypass encryption or TRIM: it only removes the API/Scoped Storage barrier. It allows scanning the *free space* of external partitions if one could do raw reads, but Android does not provide a raw block read API to apps (even with MANAGE_EXTERNAL_STORAGE). So the app could only read files and directories normally, not unallocated space. The app can also use `SDCardFs` via `openFileDescriptor`, but even that respects file-level permissions. Thus, all-files access is mainly useful to see all remaining files (not really for deleted blocks).  

- **With ADB/PC connected:** If the user connects the phone to a PC and runs ADB commands (with USB debugging enabled), more becomes possible, but this is outside a pure “Android app” scenario. A custom app could instruct the user to use `adb backup` or similar, but modern Android disables full backups of arbitrary data without root. A Windows companion could use `adb pull` to get `/data/media` if root is present. 

In summary, for a custom app on Android 14:
  - *Without root:* Only high-level, documented APIs and file lists. It can recover **media via existing records** (including any “trash” APIs exposed by OEM), and can search obvious caches. It **cannot** read deleted bits.  
  - *With root:* It can do low-level recovery (block scanning) similar to desktop tools, so it could in principle recover data from `/data/media` at the moment of deletion.  
  - *Special perms:* `MANAGE_EXTERNAL_STORAGE` allows sweeping external storage (including SD) but still through file-APIs; it doesn’t grant block access.  
  - *Backups:* If a backup archive exists (e.g. user’s Google Backup or a previous local copy), the app could parse that as a “recovery” source, but that’s really just reading a backup.  

# Proposed Recovery System Architecture  
A robust photo/video recovery app for modern Android should prioritize all *non-intrusive* sources first, without claiming false positives. For example:  

- **1. Trash/Bin:** Query the system trash. On Android 11+, the standard way is to use `MediaStore` with `MediaStore.VOLUME_EXTERNAL_PRIMARY`, which on some devices includes “deleted but not yet purged” items. If Samsung’s One UI exposes a public API or folder for Trash (not documented), try reading it (though likely not possible without root). This is *documented evidence* if available. If a photo is found in Trash, label it “Original file (in Trash)” and offer to restore.  

- **2. MediaStore scan:** Query MediaStore for images/videos. All current files here are originals. If the user deleted a file and it is still indexed (which should not happen long), it will reappear. (Edge case: maybe a media scanner hasn’t run yet.) Classify these as “Original (intact)”.  

- **3. Accessible FS locations:** Using SAF or MediaStore, enumerate media directories (DCIM, Pictures, Movies, Downloads, etc.) for any recoverable files. For each image/video found in `/storage/emulated/0/` or in an app-specific media folder, label as “Original” if the full file exists.  

- **4. Thumbnails and caches:** Look for lower-resolution copies:  
  - Check `MediaStore.Images.Thumbnails` for thumbnails of the requested media. (This is very limited utility nowadays.)  
  - Scan common cache locations that the app can read (e.g. `/Android/data/com.whatsapp/Media/WhatsApp Images` if using legacy storage or MediaStore). Classify recovered pictures here as “Cached copy” or “App duplicate”.  
  - If the app had previously generated its own thumbnails of photos, offer those (but such a scenario is unusual).  

- **5. Documented duplicates:** If the same image exists in a cloud-synced folder or in another app’s folder (for example, WhatsApp often auto-saves images to DCIM/ or a WhatsApp folder), include them. Mark as “Original (from <app> cache)”.  

- **6. Raw carving (if allowed):** Only attempt if on a rooted device. Perform a raw scan of the flash’s free space for known file signatures. For each match:  
  - Reconstruct the file as best as possible. If the file appears complete (header+footer or container length matches), label as “Reconstructed (carved)”. If only a fragment, label “Partial/corrupted”.  
  - Because carving loses the original name/location, record that it is an *unknown* original source. (Do **not** claim these as definitive recoveries; present them as forensic recoveries.)  
  - Note that JPEG can often be reconstructed but video (MP4) often fails mid-stream. Mark videos carefully as “Possibly incomplete”.  

- **7. Verify with hash or size:** If carving recovers a file identical to one already found (by name or by content), mark it as duplicate and de-duplicate the list.  

Each recovered item is tagged with its provenance: e.g. *“Original”* (file found intact), *“Trash bin (system)”*, *“Cached copy”*, *“Thumbnail”*, *“Reconstructed (signature scan)”*, *“Duplicate”*, *“Metadata only”* (if only a DB entry exists). The UI must not call a thumbnail a “recovery” of the photo. For example, finding `/DCIM/.thumbnails/xyz.jpg` is only a thumbnail. We would label it “Thumbnail (128×128)” and not confuse with the real photo.  

**Never claim more than what was actually retrieved.** For instance, if only a fragment of the image is carved, label it “Partial image recovered (some data missing)”. If only an EXIF header is found, say “Metadata-only (no image)”. This honesty prevents misleading the user.  

# Backup vs. Recovery: Key Distinction  
It’s crucial to understand that recovery is a *fragile* last resort, not a substitute for backup. On flash-based Android:  
- **Unpredictable erase:** TRIM and wear-leveling can erase deleted data at any time. Even if a recovery tool finds a file minutes after deletion, the next background trim may instantly destroy it.  
- **Encryption:** On encrypted devices, deleted data is cryptographically inaccessible. The only way to truly “recover” encrypted files is to have had a backup of them.  
- **Partial losses:** Even with raw carving, fragmentation and partial overwrite can yield incomplete files.  
- **App limitations:** As discussed, a non-root app can’t scan raw space at all. Many “recovered” items may simply be copies or thumbnails.  

A **backup** system (cloud sync, scheduled dumps to SD/PC, etc.) avoids these issues: it keeps a faithful copy of every file. Recovery software must be careful to say “found a *copy* of X in cache” rather than “recovered X”. Good backup can guarantee recovery, whereas file carving at best *tries* and often fails. 

Therefore, educate users: missing photos may be gone forever unless they had a backup. This research’s purpose is to clarify those boundaries.

The above tables summarize which recovery methods work in each scenario. In practice, an on-device app should rely on **MediaStore and accessible copies first**. It can *offer* to perform a root-privileged raw-scan if it detects root, but with clear warnings about fragmentation and incompleteness. Any claim of recovery must specify whether it’s an *original* file or merely a *fragment/thumbnail*. 

**Bottom line:** On a modern Android 14 device like the Galaxy A05s, a normal app (no root) can only recover photos that still exist in some form: in the system Trash, in app caches it can read, or in cloud backups (through an API). It **cannot** undelete blocks from the internal flash. Root access unlocks raw-carving possibilities, but even then encryption and TRIM severely limit what’s recoverable. Many photos, once “permanently” deleted, are simply unrecoverable without a prior backup. Users should be counseled that **backup is the only reliable solution**, and recovery tools are a last resort with no guarantees.
